This document records the complete recovery of the **v10104** format and the

## 1. v10104 â€” static byte substitution (SOLVED)

### 1.1 Format

Every `.lua` entry is exactly as long as its source: one source byte is
replaced by one cipher byte.  It is a fixed, global substitution table (same
for every game and every file).

```text
cipher[i] = SBOX[source[i]]          # length-preserving
source[i] = INV_SBOX[cipher[i]]
```

The first bytes of a v10104 Lua entry decode as expected:

```text
cipher:  37 37 37 14 â€¦      ("777\x14")
plain :  2d 2d 2d 0a â€¦      ("---\n")
```

i.e. the familiar `---\n--- Generated by EmmyLuaâ€¦` header.

### 1.2 Recovering the table

The table is recovered as `cipher byte -> plaintext byte` pairs from any
known plaintext (e.g. the same path in v10103, which is unencrypted).  The map
is single-valued and was verified over the whole corpus:

* 172 distinct cipher bytes occur in the corpus; they map to 172 distinct plain
  bytes.
* Decoding every v10104 entry with these 172 pairs reproduces the expected
  source MD5 for **317 / 318** engine files in **each** of g1019 and g1042.
* The single mismatch in both games is `lua/plugins/new_vip/new_vip.lua`.
  Its `sandboxol` MD5 is the MD5 of the **v10103** copy (6349 bytes,
  `c1ac6291â€¦`); the shipped v10104 file is a hot-fixed variant (6346 bytes).
  This is a stale checksum, not a decryption error.
* The remaining 84 byte values never occur as ciphertext in the corpus, so the
  table is complete *for every shipped file*; a full 256-entry table can be
  completed by the same known-plaintext harvest from new packages.

### 1.3 Reference code

`howto/data/v10104_sbox.json` contains the recovered pairs:

```json
{
  "cipher_to_plain": { "<int cipher>": "<int plain>", â€¦ },
  "plain_to_cipher": { â€¦ }
}
```

Minimal decoder:

```python
import json

source = bytes(c2p.get(b, b) for b in cipher)
```

A tool that harvests pairs from known sources, decodes a package, and verifies
against the `sandboxol` / `checksums.md5` lists is
`howto/scripts/v10104_harvest.py`.

## 2. v10105 â€” the 2â†’3 byte codebook format

### 2.1 Container and validation

`plugin.zip` (a published game map package):

| entry | content |
|---|---|
| `setting/â€¦`, `config.yml` | plaintext JSON/CSV/YAML |
| `checksums.md5` | `md5(shipped bytes) *path` â€” validates the **ciphertext** |
| `lua/sandboxol` | base64 of `"<md5> *Scripts/Engine/<path>"` â€” source MD5s (engine files only) |
| `lua/**/*.lua` | encrypted, see below |

The runtime downloads the package, unzips it and verifies `checksums.md5`
(i.e. the encrypted files).  The Lua loader then consumes the Lua entries.

### 2.2 Plaintext layout

For every encrypted Lua entry the plaintext stream is:

```text
[ source bytes ][ "--[[ <random bytes> --]]" ]
```

The trailing comment is deterministic pad; its length varies and is what makes
the ciphertext length unpredictable.  In a correct decode the `--[[` marker is
visible immediately after the source and the stream ends with `--]]`.

Before the encoded stream there is a raw per-file header of `off` bytes:

* `off` is 0 for three tiny entries, otherwise 13â€¦54;
* `header[0]` is in `5..10`;
* `header[-1]` is `0x00` (a decisive alignment oracle: the true `off` always
  has `cipher[off-1] == 0`);
* the header looks like a random per-file salt/nonce.  Its role as a KDF seed
  has **not** been identified (see Â§2.6).

The encoded stream starts at `off` and is read three bytes at a time.

### 2.3 The 2â†’3 triple

```text
cipher triple:   b0  b1  b2
plain pair:      p0  p1
```

The pair is encoded **independently per byte**:

```text
b0 = low 7 bits  of code0(p0)
b1 = (code0(p0) >> 7) << 4 | (code1(p1) >> 8)     (8 bits)
b2 = low 8 bits  of code1(p1)

code0(p)  = (b1 >> 4) << 7 | b0          # 11-bit code for p0
code1(p)  = (b1 & 7)   << 8 | b2         # 11-bit code for p1
```

Equivalently, each plaintext byte has an 11-bit code, and two codes are packed
into three bytes with two unused bits.  For decoding:

```text
p0 = D0[(b0, b1 >> 4)]          # D0: 11-bit code -> plaintext byte
p1 = D1[(b2, b1 & 7)]           # D1: 11-bit code -> plaintext byte
```

`D0` and `D1` are two **different, per-file** tables.  Properties verified on
1289 recovered files (zero conflicts):

* `D0[(b0, b1>>4)]` is single-valued (depends only on the plaintext byte at an
  even stream position);
* `D1[(b2, b1&7)]` is single-valued (odd stream positions);
* the pairâ†’triple map is a function: the same plaintext pair always yields the
  same triple anywhere in the file (and in any file with identical content);
* tables are **content-derived**: the same file content gives byte-identical
  ciphertext/tables across games; a different content gives different tables;
* within one file, `D0 â‰  D1`.

The two tables together are a 2Ã—(256Ã—11-bit) codebook.  This is the same
*shape* as the keyfile cipher in `02-content-cipher.md`, but the
`apply_list`/keylist model does **not** reproduce it: no list from the engine
or plugin keyfiles matches, and the per-byte map is not affine, not a
nibble substitution and not a variant of the v10104 S-box.

### 2.4 Length rule (important)

Let `N = (len(cipher) - off) / 3` (encoded pairs) and `L` the source length:

```text
total plaintext bytes = 2 * N
pad                   = 2 * N - L
pad in [16 .. 61]                       (observed 18..59 on validated files)
```

A candidate source that is much shorter than `2N - pad` is a truncated prefix
and must be rejected.  This rule corrected 18 false matches (files whose older
version was a strict prefix of the v10105 source).

### 2.5 Recovery methods that work

1. **Exact known plaintext** â€” for an entry, take the same relative path from
   the plaintext packs (g1019 v10068â€¦v10103, g1042 v10103) or from already
   recovered versions; try every offset 0â€¦180 and verify the pairâ†’triple
   encoding over the whole file.  The map is content-based, so any version with
   identical bytes works, including another game.

2. **Structural verification** â€” build
   `p0 -> (b0, b1>>4)` and `p1 -> (b2, b1&7)`; the true source gives zero
   conflicts.  This rejects wrong-length/truncated candidates even when they
   "look" consistent prefix-wise.

3. **Checksums** â€” `lua/sandboxol` gives the exact source MD5 for engine
   files; `checksums.md5` gives the ciphertext MD5.  A recovered source must
   match the former.

4. **Edit-subset search** â€” the v10105 source is often an intermediate version
   between two known ones.  Compute the difflib edit script between version A
   and B, apply subsets of B's edits to A, and keep a candidate iff the
   pairâ†’triple map has zero conflicts.  This is decisive and recovered, e.g.
   `annotation.lua` = v10106 minus one inserted annotation block, and
   `packet/PidPacketHandler.lua` = v10101 plus one edit.

5. **Iterative crib decoder** â€” for entries whose content is unique:
   * initialise vote tables from any crib (`crib byte -> code`) at the true
     offset;
   * decode the stream;
   * align the crib to the decoded text with `difflib`;
   * re-vote from **all** aligned positions (including `replace` blocks, with
     fallback to the initial votes for symbols not covered);
   * iterate, then cut the source at the last `--[[` and verify the MD5.

   This recovered `StringUtil.lua`, `DressUtil.lua`, `IPayActivity.lua`,
   `GUICommonAdActivityItem.lua` exactly (MD5 proof).

6. **Pad-length brute force** â€” if the decoded bytes are right but the
   source/trailer boundary is uncertain, try every `pad` in 16â€¦61 and compare
   `md5(prefix)` with the known source MD5.

### 2.6 What remains

The **per-file KDF** that turns the header/salt into `D0`/`D1` is still
unknown.  This matters only for files whose exact source is not present
anywhere in the corpus and whose content changed only in v10105.  A
known-plaintext/crib attack cannot recover those without the KDF.

Scripts (Python 3.12, standard library only; paths at the top of each file):

Typical runs:

```powershell
python howto\scripts\v10104_harvest.py --game g1042 --version v10104 --write
```

## 5. Notes on wrappers

The trailing `--[[<random>--]]` comment is part of the v10105 plaintext and is
**not** the source.  When cutting a decoded stream always cut at the last
`--[[` (the marker is ASCII and decodes reliably once the tables are good) and
verify the resulting length against the pad rule and the source MD5.  Do not
confuse it with the anti-tamper `--[[R1]]/--[[R2]]/--[[R3]]` wrapper used by
v10106+ engine files.
